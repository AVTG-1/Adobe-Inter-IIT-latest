Architecture Overview

Adobe Image Editor follows a layered architecture pattern with clear separation between frontend, backend, and external services. The system is designed for scalability, maintainability, and extensibility with AI-powered intelligent workflows at its core.

Backend Architecture

Layered Architecture Pattern

The backend follows a strict 3-layer architecture that separates concerns and promotes maintainability:

🎯

Orchestration Layer

Location: app/orchestration/

Handles API endpoints, WebSocket connections, workflow coordination, and user interaction.

Components:

  • FastAPI application
  • Execution engine
  • LLM service integration
  • State store management
⚙️

Core Layer

Location: app/core/

Contains business logic, data models, and core services that power the application.

Components:

  • Pydantic models & schemas
  • Storage service (GCS/Local)
  • Third-party service clients
  • Image processing utilities
🤖

Experts Layer

Location: app/experts/

Specialized AI agents and tools for complex image processing tasks.

Components:

  • Base agent (TAO pattern)
  • Inpainting agent
  • Relighting agent
  • LangChain tool wrappers

AI-Powered Workflow System

Tree-Based State Management

One of the key innovations is the tree-based state management system that enables non-linear editing with branching, versioning, and macro recording. 

Initial Image (Root Node)
       │
       ▼
  ┌────────┐
  │ Crop   │
  └────┬───┘
       │
       ├─────────┬─────────┐
       │         │         │
  ┌────▼───┐ ┌──▼────┐ ┌──▼────┐
  │Brighten│ │ Blur  │ │Contrast│  (Multiple Branches)
  └────┬───┘ └───┬───┘ └───┬───┘
       │         │         │
       ▼         ▼         ▼
   [Version 1][Version 2][Version 3]

User can:
• Switch between any version
• Refine any node to create new branch
• Record macro from path
• Apply macro to new images

LLM Planning Flow

1. User Input
   ├─ Natural language prompt
   ├─ Reference image (optional)
   └─ Original image
        │
        ▼
2. LLM Analysis (Gemini)
   ├─ Analyzes image content
   ├─ Parses user intent
   └─ Generates multi-step plan
        │
        ▼
3. Plan Generation
   {
     "steps": [
       {"tool": "crop", "params": {...}},
       {"tool": "brightness", "params": {...}},
       {"tool": "filter", "params": {...}}
     ],
     "reasoning": "..."
   }
        │
        ▼
4. Execution Engine
   ├─ Execute steps sequentially
   ├─ Send WebSocket updates
   └─ Handle errors (retry/skip)
        │
        ▼
5. Result Delivery
   ├─ Final image URL
   ├─ State tree updated
   └─ Client displays result

Communication Patterns

REST API

Used for simple request-response operations like health checks and single-shot edits. 

POST /api/v1/edit/general
Content-Type: application/json

{
  "image_url": "https://storage.googleapis.com/...",
  "operations": [
    {"type": "brightness", "value": 1.2},
    {"type": "crop", "x": 0, "y": 0, "width": 800, "height": 600}
  ]
}

Response:
{
  "job_id": "uuid",
  "status": "completed",
  "result_url": "https://...",
  "processing_time_ms": 1234
}

WebSocket Protocol

Used for real-time AI workflows with step-by-step progress updates. 

// Client connects
ws://localhost:8000/ws/client_123

// Client sends
{
  "action": "start_processing",
  "data": {
    "prompt": "Make this photo more vibrant and crop to square",
    "image_url": "https://...",
    "session_id": "session_456"
  }
}

// Server sends (multiple events)
{
  "type": "step_start",
  "step_index": 0,
  "tool": "crop",
  "params": {...}
}

{
  "type": "path_update",
  "node": {
    "id": "node_789",
    "image_url": "https://...",
    "thumbnail_url": "https://..."
  }
}

Security Considerations

⚠️ Production Security: This codebase includes placeholder credentials. Before deploying to production, ensure all API keys and service account credentials are properly secured using environment variables and secret management systems.
  • API Keys: Stored in environment variables, not committed to Git
  • GCS Service Account: JSON key files excluded via .gitignore
  • CORS: Configure allowed origins in production
  • Rate Limiting: Implement rate limiting for API endpoints
  • Input Validation: Pydantic models validate all inputs
  • File Upload: Validate file types and sizes

Scalability & Performance

Backend Scalability

  • Async Processing: FastAPI async endpoints for concurrent request handling
  • Service Separation: Image processing can be moved to separate microservices
  • Caching: Redis can be added for session state and result caching
  • Load Balancing: Multiple backend instances can run behind a load balancer
  • Queue System: Celery/RabbitMQ for long-running tasks

Frontend Performance

  • Image Optimization: Thumbnails and progressive loading
  • Lazy Loading: Components and screens loaded on demand
  • Caching: Local image caching to reduce network requests
  • Animations: Native driver for smooth 60 FPS animations
  • Memoization: React.memo and useMemo to prevent unnecessary renders

Design Patterns

Pattern Location Purpose
Layered Architecture Backend (3 layers) Separation of concerns, maintainability
Service Layer Frontend services/ Abstract API calls and business logic
Factory Pattern Service clients Create service instances (Imaginary, OpenCV)
Observer Pattern WebSocket manager Real-time event broadcasting
Command Pattern Image operations Encapsulate edit operations as objects
TAO Pattern AI agents Think-Act-Observe for AI agents
Repository Pattern Storage service Abstract data access (GCS/Local)
